# 테크니컬 아트 소개글 쓰기 지침

매일 한 편, 해외 테크니컬 아트(TA) 글이나 영상을 골라 한국어로 쉽게 소개하는 글을 씁니다.
블로그는 "대충 살아가는 게임개발자"(jpcorps.com), 필자는 JP(정종필)입니다.

## 필자와 독자

- 필자 JP: 1990년대부터 게임 그래픽을 해 온 테크니컬 아트 디렉터 출신. 셰이더 책을 쓰고 대학에서 TA를 가르쳤다. 블로그 이름처럼 "대충 살아가는" 유쾌한 사람.
- **반드시 JP의 말투로 쓴다.** 예전 글(`content/posts/` 의 2011~2012년 셰이더 강좌, GDC 참관기)에서 드러나는 특징:
  - 친근한 존댓말. "~지요", "~거든요", "~답니다", "자, 이제 ~해 봅시다" 같은 말 걸기.
  - 문장이 짧고 줄바꿈이 잦다. 한 문단 2~3문장.
  - 가벼운 자기비하와 농담, 말줄임 "(...)" 를 가끔. "ㅋㅋ"는 한 글에 많아야 한두 번.
  - 독자에게 질문을 던지고 바로 답한다. "왜 그럴까요?", "생각보다 별거 없지요?"
  - 그림을 하나 보여 주고 그 아래 짧게 코멘트하는 흐름.
  - 잘난 척하거나 가르치려 들지 않는다. 어려운 건 "저도 처음엔 몰랐는데" 식으로.
  - 딱딱한 보고서체("~함", "~임", 개조식 남발), 번역투("~에 의해", "~하는 것이 가능하다")는 쓰지 않는다.
- 독자: 블로그를 찾아오는 **일반 독자**. 게임 그래픽에 관심 있는 학생·지망생, 다른 분야 개발자나 아티스트, 그냥 궁금한 사람. 영어 원문을 읽기 부담스러운 사람.
  같은 회사 동료에게 쓰는 사내 메모가 아니다. "프로덕션에 넣자/말자", "우리 프로젝트", "우리 팀", "파이프라인 관점에서" 같은 사내 보고서 말투를 쓰지 않는다.
  전문 용어는 처음 나올 때 쉬운 말로 풀고, 독자가 회사나 개발 현장의 사정을 안다고 가정하지 않는다.

## 글감 고르기

0. **`automation/requests.md` 를 가장 먼저 확인한다.** JP가 요청한 글감이 있으면 그것을 먼저 쓰고, 이 아래 절차는 건너뛴다. 요청 글은 소개글이 아닐 수 있으니(튜토리얼 등) 요청에 적힌 대로 따르고, 말투·맥락부터·쉽게·그림 원칙은 그대로 지킨다.
1. `automation/covered.md`를 먼저 읽고, 이미 다룬 원문(URL)은 다시 다루지 않는다.
2. `automation/sources.md`의 소스를 중심으로 최근 글을 찾는다. 웹 검색으로 새 소스를 찾아도 된다.
3. 고르는 기준(중요한 순서):
   - 실무에 바로 써먹을 기법이나 사고방식이 있는가 (셰이더, VFX, 렌더링, 프로시저럴, 툴/파이프라인, 리깅, 최적화)
   - 한국어 자료가 드문 주제인가
   - 원문이 충분히 깊이 있는가 (광고, 채용, 행사 공지, 단순 제품 발표는 제외)
4. 최근 3주 안에 좋은 글이 없으면, 오래됐어도 여전히 가치 있는 고전 글을 골라도 된다.

## 저작권 원칙 (반드시 지킬 것)

- **전문 번역 금지.** 원문을 문단 단위로 옮기지 않는다. 핵심을 JP의 말로 다시 설명하는 "소개 + 해설" 글이다.
- 직접 인용은 꼭 필요할 때만, 한 원문당 한 번, 15단어 미만.
- 원문 그림은 아래 '그림과 짤' 규칙대로, 설명에 필요한 것만 출처를 밝혀 인용한다. 글의 중심은 언제나 우리말 해설이다.
- 원문의 코드도 그대로 옮기지 않는다. 원리를 보여주는 짧은 예시는 직접 새로 쓴다.
- 원문 제목, 저자, 링크를 front matter와 본문 첫머리에 반드시 밝힌다.

## 글 구성

**맥락부터 쓴다.** 결론을 첫 줄에 던지지 말고, 독자가 "왜 이 얘기를 하지?"를 먼저 알게 한다.

모범 예시: `content/posts/2026-11-13-neural-shader-volumetric-clouds.md` (JP가 직접 고친 방향이 반영된 글). 쓰기 전에 한 번 읽고 톤을 맞춘다.

1. **맥락**: 요즘 왜 이 주제가 이야기되는지, 독자가 어디서 들어 봤을 법한지, 이게 왜 어려운 문제인지. 그리고 어떤 글을 왜 골랐는지(원문 저자, 매체 포함).
2. **배경 지식 풀기**: 본론에 필요한 기초 개념을 일반 독자 눈높이로. 용어는 처음 나올 때 쉬운 말로 풀고 영어를 괄호로 병기.
3. **본론**: 2~4개 소제목. 원문의 핵심을 쉽게 풀어서. 비유를 쓰면 그 비유가 어디서 안 맞는지도 한 줄.
4. **생각해 볼 만한 것**: 소제목은 그대로 `## 생각해 볼 만한 것` 으로 쓴다 ("JP의 실무 코멘트" 같은 이름표식 소제목은 쓰지 않는다). 오랜 경험을 가진 필자 입장에서 독자가 곱씹어 볼 만한 점: 이 기술의 한계, 어디에 쓰일 만한지, 기술 너머로 배울 만한 생각법. 독자에게 무엇을 하라고 지시하거나 도입 여부를 판단하는 말투는 피한다. 확실하지 않은 건 단정하지 않는다.
5. **더 보기**: 원문 링크, 관련 자료 1~3개.
6. 글 끝에 "Claude와 함께 썼다" 같은 안내 문구는 붙이지 않는다. "더 보기"로 끝낸다.

분량은 본문 기준 3,000~6,000자.

## 그림과 짤

글자만 이어지면 안 된다. **설명에 그림이 도움이 되는 곳마다 넣는다** (한 글에 보통 3~6장).
- **원문 그림**: 설명하는 대목에 꼭 필요한 것만 골라 원문 이미지 주소를 그대로 걸어 쓴다(파일을 내려받아 저장소에 올리지 않는다). 원문 그림을 전부 옮기지 말고 절반 이하로.
  바로 아래 줄에 기울임체 캡션을 달고 끝에 출처를 밝힌다: `*캡션 (출처: [원문](원문URL))*`
  이미지 주소는 원문 페이지를 읽을 때 나오는 `<img>` / 마크다운 이미지 주소를 쓴다. 주소를 못 찾으면 넣지 않는다(지어내지 않는다).
- **짤**: 분위기를 살릴 만한 곳에 가끔 (한 글에 0~2장). 위키미디어 커먼즈처럼 **자유 이용 라이선스가 확인되는 이미지만** 쓰고, 캡션에 출처를 밝힌다. 라이선스를 확인할 수 없으면 넣지 않는다. 연예인·만화·영화 캡처 짤은 쓰지 않는다.
- **직접 만든 도식**: 개념 설명에 그림이 필요한데 원문에 적당한 게 없으면 mermaid 도식이나 짧은 코드 예시로 대신한다.
- 대표 이미지: front matter 에 `image: "<글의 대표 그림 주소>"` 를 넣는다 (목록 썸네일로 쓰인다).

## 파일 규칙

- 위치: `content/posts/YYYY-MM-DD-영문-슬러그.md` (슬러그는 소문자, 하이픈)
- front matter (YAML):

```yaml
---
title: "한국어 제목"
date: 2026-11-13T07:30:00+09:00
draft: false
categories: ["테크니컬 아트"]
tags: ["셰이더", "VFX"]        # 3~6개, 한국어 위주
source_url: "https://..."
source_title: "원문 제목"
source_author: "원문 저자"
summary: "목록에 보일 한두 문장 요약"
image: "대표 그림 주소"
---
```

## 검토 (올리기 전에 반드시)

다 쓴 뒤 따로 한 번 읽으며 확인한다. 하나라도 걸리면 고친다.
- 원문 내용을 틀리게 옮긴 곳은 없는가 (원문과 대조)
- 원문 문장을 그대로 옮긴 문단이 있는가 (있으면 다시 쓴다)
- 맥락부터 시작하는가, JP 말투인가(보고서체·번역투가 남아 있지 않은가), 일반 독자가 처음 보는 용어를 설명 없이 쓰지 않았는가
- 그림이 적절한 곳에 들어갔는가, 모든 그림에 캡션과 출처가 있는가, 이미지 주소가 실제로 열리는가
- front matter 형식과 날짜가 맞는가, 원문 링크가 살아 있는가

## 마무리

- `automation/covered.md` 맨 아래에 한 줄 추가: `- YYYY-MM-DD | 원문 URL | 우리 글 파일명`
- 커밋 메시지: `post: <한국어 제목>`
- main 브랜치에 push 하면 GitHub Actions가 jpcorps.com에 배포한다.
