> 원문: [Neural Shaders, Explained With Clouds](https://charlesgrassi.dev/blog/neural-volumetric-clouds/) — Charles Grassi (2026년 8월)

결론부터 말씀드리면 이렇습니다. 구름 레이마칭 셰이더에서 **빛이 산란되는 계산 딱 하나**를 작은 신경망(곱셈-덧셈 512번짜리)으로 바꿨더니, 기존 근사식이 태양 각도에 따라 정답 대비 0.2배에서 2.2배까지 오락가락하던 밝기가 대부분의 각도에서 ±10% 안으로 들어왔습니다. 대가는 구름 패스 GPU 시간 약 20% 증가. 그리고 이 글의 진짜 교훈은 신경망 자체보다 "정답 렌더러를 먼저 만들고, 한 가지만 바꾸고, 여러 조건에서 숫자로 재라"는 작업 방식에 있습니다.

## 원문 소개

Charles Grassi 가 자기 블로그에 올린 글로, 유니티 6 URP 에서 직접 만든 뉴럴 구름 셰이더의 제작기입니다. "뉴럴 셰이더(neural shader)"라는 말은 요즘 GDC 나 엔비디아 발표에서 자주 들리는데, 막상 TA 입장에서 "그래서 셰이더 안에서 뭘 어떻게 한다는 거냐"를 손에 잡히게 설명한 한국어 자료는 거의 없습니다. 이 글은 텐서 코어 같은 특수 하드웨어 없이, 평범한 HLSL 프래그먼트 셰이더에서 손으로 행렬 곱을 짜서 돌립니다. 그래서 TA 가 따라 해 볼 수 있는 거리 안에 있다는 점이 좋아서 골랐습니다.

## 1. 뉴럴 셰이더란: 공식을 유도하는 대신 '정답 예시'로 학습시킨다

셰이더는 보통 누군가 유도한 공식을 씁니다. 그런데 구름은 빛이 안에서 수천 번 튕기기 때문에 깔끔한 공식이 없습니다. 그래서 게임은 그럴듯한 근사식으로 속여 왔죠.

뉴럴 셰이더는 그 계산 하나를 **작은 신경망(MLP, 다층 퍼셉트론)** 으로 바꿉니다. 느리지만 정확한 방법(여기서는 패스 트레이싱)으로 "이 상황에선 이 밝기가 정답"인 예시를 수십만 개 만들고, 신경망이 그걸 흉내 내도록 오프라인에서 학습시킨 뒤, 학습된 숫자(가중치)만 게임에 넣는 겁니다.

비유하자면 "길을 외워서 운전하기"입니다. 지도(공식)는 없지만 수없이 다녀 본 경험으로 감을 익히는 거죠. 다만 이 비유가 틀리는 곳도 있습니다. 사람은 처음 가는 동네에서도 어느 정도 추론하지만, 이 신경망은 학습 때 본 상황에서 멀어질수록 쉽게 틀립니다. 원문도 이 점을 아주 솔직하게 다룹니다.

## 2. 무엇을 바꾸고, 무엇을 입력으로 주나

구름 레이마칭(ray marching)은 시선 방향으로 조금씩 전진하면서 매 스텝마다 두 가지를 묻습니다.

- 여기서 빛이 얼마나 **가려지나**(감쇠, extinction) — 밀도만 알면 되는 쉬운 계산
- 여기서 빛이 얼마나 **카메라 쪽으로 산란되나**(인스캐터, in-scattering) — 진짜 어려운 계산

원문은 **인스캐터 항 하나만** 신경망으로 바꾸고, 스텝 진행·감쇠·누적은 그대로 둡니다. 이게 핵심입니다. 나머지가 똑같으니 비교가 공정해지거든요.

신경망 입력은 스텝마다 13개입니다.

- 현재 지점 주변의 평균 밀도 6개 (반경 6m 에서 192m 까지 두 배씩)
- 태양 쪽 방향으로 잰 같은 종류의 밀도 6개 (가장 중요한 단서)
- 시선과 태양 사이 각도의 코사인 1개

평균 밀도는 밀도 볼륨 텍스처의 밉맵 피라미드에서 한 번씩 읽어 오니, 입력 하나가 텍스처 샘플 한 번입니다. 단위를 미터로 잡은 이유는 구름 크기나 베이크 해상도가 바뀌어도 입력의 의미가 같게 유지되도록 하기 위해서라고 합니다. 출력은 3개로, 태양광·하늘광·지면 반사광입니다.

구조는 13 → 16 → 16 → 3 입니다. 계산해 보면 13×16 + 16×16 + 16×3 = 512, 그래서 "곱셈-덧셈 512번"입니다. 활성화 함수는 ReLU 를 제곱한 것(squared ReLU)을 씁니다. 이 선택에도 사연이 있는데 아래 '시행착오'에서 다룹니다.

원리만 보여 드리려고 제가 새로 쓴 아주 단순한 HLSL 스케치입니다(원문 코드가 아니고, 가중치 배치도 임의로 정했습니다).

```hlsl
// 은닉층 하나: out[j] = act( b[j] + Σ w[j][i] * in[i] )
float SqRelu(float x) { float r = max(x, 0); return r * r; }

void Dense13x16(float inV[13], out float h[16])
{
    [unroll] for (int j = 0; j < 16; j++)
    {
        float s = _B1[j];
        [unroll] for (int i = 0; i < 13; i++)
            s += _W1[j * 13 + i] * inV[i];   // 상수 버퍼의 가중치
        h[j] = SqRelu(s);
    }
}
```

특별한 라이브러리 없이 이런 곱셈-덧셈 루프를 몇 층 쌓은 게 전부입니다. "AI"라는 말에 겁먹을 필요가 없는 크기죠.

## 3. 얼마나 맞고, 얼마나 비싼가

평가는 태양을 0°에서 180°까지 15°씩 13개 위치로 돌리면서, 패스 트레이싱 정답 대비 밝기 비율을 잽니다(1.0 이 정답).

- 기존 근사(헨예이-그린스타인 위상 함수 + Wrenninge 식 다중 산란 옥타브 3개): 0°에서 0.21, 90°에서 0.67, 180°에서 2.17. 태양 위치에 따라 약 10배 차이.
- 뉴럴 버전: 13개 중 12개 위치에서 0.90~1.01. 다만 태양을 정면으로 바라보는 180°에서는 1.20 으로 튑니다.

180°가 어려운 이유는 이 각도에선 빛 대부분이 한 번만 튕기고 통과해서 아주 좁고 밝은 스파이크가 생기는데, 작은 신경망이 그걸 잘 못 잡기 때문이라고 설명합니다.

비용은 노트북 RTX 4080, 유니티 6 URP, D3D12 기준 구름 패스만 재서 4K 에서 1.88ms → 2.32ms 정도, 대략 20% 증가입니다. 흥미로운 건 텍스처 읽기는 오히려 줄었다는 점입니다(기존 14회 순차 → 12회 독립). 늘어난 비용은 512번의 곱셈-덧셈을 하나하나 손으로 하기 때문인데, DX12/Vulkan 의 협력 벡터(cooperative vectors)를 쓰면 이걸 텐서 유닛에 통째로 맡길 수 있지만 유니티 HLSL 에선 아직 쓸 수 없다고 합니다.

## 4. 시행착오가 제일 값진 부분

원문에서 TA 에게 가장 도움이 되는 건 실패담입니다. 몇 가지만 추리면:

- **세제곱근으로 바꿔서 학습시켰더니 밝기가 반토막.** 노이즈 섞인 정답을 비선형 곡선에 통과시킨 뒤 평균을 내면, 원래 값의 평균과 달라집니다. 원값 그대로 학습하니 해결.
- **ReLU 의 경계선이 화면에 껍질 모양 주름으로 보임.** 조각마다 평평한 함수라서 생긴 문제로, 제곱 ReLU 로 바꿔 해결(곱셈 하나 추가). 엔비디아 가이드가 권하는 Leaky ReLU 도 같은 이유로 주름이 다시 생겼다고 합니다.
- **학습 샘플 위치가 정확도를 좌우.** 구름 안에 고르게 점을 뿌리는 대신, 카메라 광선이 처음 닿는 곳 위주로 뽑았더니 눈에 잘 보이는 밝은 영역의 정확도가 0.34 → 0.70 으로 올랐습니다. 신경망은 그대로인데요.
- **검증용 데이터를 잘못 골라서 엉뚱한 결론.** 가장 두꺼운 구름을 시험용으로 빼 두었더니 '일반화'가 아니라 '외삽' 시험이 되어 버려서, 망이 작다고 오판할 뻔했다고 합니다.

유니티 쪽 실무 함정도 하나 있습니다. 셰이더 상수 배열의 길이가 그 세션에서 처음 올린 크기로 고정돼서, 나중에 망 구조를 키우면 새 칸이 0 으로 읽혀 에러 없이 하얀 덩어리가 나온답니다. 그래서 배열을 고정 크기로 패딩하고, 마지막 칸에 확인용 값(sentinel)을 넣어 없으면 기존 근사식으로 돌아가게 했다고 합니다. 이런 건 직접 당해 봐야 아는 종류라 기억해 둘 만합니다.

## 생각해 볼 만한 것

- **아직은 실험 단계의 기술입니다.** 원문도 한계를 분명히 적었습니다. 구름 하나만 학습했고, 구름의 성질(재질 값)이 학습된 숫자 안에 고정돼 있어서 아티스트가 값을 바꿀 수 없고, 거리에 따라 디테일을 줄이는 처리(LOD)도 없습니다. 구름 모양이나 색감을 손볼 때마다 다시 학습시켜야 한다는 건, 게임을 만드는 입장에서는 꽤 큰 부담입니다.
- **휴대폰 게임이라면 이야기가 또 다릅니다.** 데스크톱 그래픽카드에서 20% 더 무거워졌다면, 성능 여유가 적은 휴대폰에서는 훨씬 크게 느껴질 수 있습니다. 이건 제 추측이고, 원문에서 직접 확인한 내용은 아닙니다.
- **기술보다 더 배울 만한 건 '재 보는 습관'입니다.** 게임 속 구름이 역광에서는 실제보다 두 배 밝고 순광에서는 다섯 배 어둡다는 사실을, 스크린샷 한 장만 봐서는 알 수 없습니다. 정답에 가까운 그림을 먼저 만들어 두고 조건을 바꿔 가며 숫자로 비교해 보는 것, 이건 신경망을 쓰지 않더라도 그래픽을 다루는 사람이라면 누구나 해 볼 수 있는 방법입니다.
- 원문은 이 기법이 쓰일 만한 다른 곳으로 피부, 여러 겹으로 된 재질, 머리카락과 천을 꼽습니다. 공통점은 "정확히 계산하면 너무 무겁지만, 몇 가지 숫자로 상황을 요약할 수 있고, 시간을 들이면 정답을 미리 만들어 둘 수 있는" 문제라는 점입니다. 앞으로 뉴럴 셰이더 소식을 볼 때 이 세 가지를 떠올리면 왜 그 분야부터 쓰이는지 이해하기 쉬울 겁니다.
